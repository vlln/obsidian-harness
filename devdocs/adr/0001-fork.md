# ADR-0001: Fork 而非 PR 或从零开始

---

## 背景

当前开源项目 [RAIT-09/obsidian-agent-client](https://github.com/RAIT-09/obsidian-agent-client) 是最接近设想的 Obsidian Agent 插件。但其产品哲学是"在 Obsidian 侧边栏嵌入聊天窗口"，而 Obsidian Harness 的产品哲学是"以 Obsidian 知识库为驾驶舱，Agent 为执行引擎"。这是根本性的产品设计差异，不是功能叠加。

---

## 决策内容

**Fork 原项目，保留 ACP 基础设施层（`acp/`、`types/`、`services/`），独立演进 UI 层和 Session 存储层。**

---

## 备选方案

### 方案 A: PR 融入原项目

向原项目提交 PR，在现有产品框架内逐步改造。

- 优点：共享社区维护成本、上游 bugfix 自动获得
- 缺点：产品哲学差异是根本性的，PR 需要大规模重写 UI 层和 Session 存储层，很可能被拒绝或需要漫长讨论妥协。两种产品哲学无法在同一个产品中共存。

### 方案 B: 从零开始，仅复用 `@agentclientprotocol/sdk`

完全不依赖原项目代码，仅使用 ACP SDK npm 包。

- 优点：完全自由的设计空间，无历史包袱
- 缺点：需要重写约 1000+ 行已验证的 ACP 集成代码（进程管理、shell 兼容、WSL 支持、权限管理、终端处理等），容易在细节上踩坑。

### 方案 C: Fork 原项目，保留 ACP 层（选择）

- 优点：ACP 基础设施已稳定验证，与产品形态完全解耦；可立即开始做产品差异化的部分；上游 `acp/` 层的 bugfix 可手动 cherry-pick
- 缺点：需要维护 fork，上游更新需手动同步；但 `acp/` 层相对稳定，维护成本可控

---

## 选择理由

ACP 基础设施层（`acp/`）是当前项目最有价值的资产，且与产品形态（侧边栏 vs 笔记入口）完全解耦。它处理的是"如何与 ACP agent 通信"，不是"如何展示 UI"。Fork 保留这层避免了重复踩坑，同时给予 UI 层完全的设计自由。

---

## 验证

不适用（此 ADR 为决策记录，非技术选型验证）。

---

## 后果

### 正面

- 立即获得稳定的多 Agent 支持（Claude/Codex/Gemini/Custom）
- 进程管理、权限系统、终端处理开箱即用
- 可专注于产品差异化部分

### 负面

- 需维护 fork，上游更新需手动 cherry-pick
- 原项目 `src/` 中与产品哲学相关的代码（UI 组件、Session 存储）需要逐步替换

---

## 约束范围

全部模块。此决策定义了项目的技术基础来源。

---

## 约束规则

| 规则编号 | 规则 | 适用范围 | 违反时如何检出 |
|----------|------|---------|--------------|
| AR-001 | `acp/` 目录的修改应优先从上游 cherry-pick，而非自行重写 | `acp/` | code review |
| AR-002 | 上游 `types/` 和 `services/` 的修改需评估是否与产品哲学冲突 | `types/`, `services/` | code review |
| AR-003 | `ui/` 和 `hooks/` 独立演进，不与上游同步 | `ui/`, `hooks/` | 无需检出 |
